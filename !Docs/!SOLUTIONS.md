## 📌 CoinLover: Защита от затирания Configs, сортировка ленты и доступ к мастер-таблице (08.09.2026)

### 1. Защита от затирания счетов на листе Configs (Google Sheets)
* **Проблема:** При внесении изменений в веб-интерфейсе (редактирование или добавление транзакции) на листе `Configs` Google Таблицы полностью затирался список счетов.
* **Причина:**
  * В `src/hooks/useTransactions.ts` расчет `updatedAccounts` выполнялся внутри функционального коллбэка React `setAccounts(prev => { updatedAccounts = ... })`. Поскольку в React этот апдейтер выполняется асинхронно, в последующий синхронный сетевой запрос уходил пустой массив `accounts: []`.
  * В `api/sheets.ts` стояла проверка `if (payload.accounts)`. В JavaScript пустой массив является truthy (`Boolean([]) === true`), поэтому бэкенд вызывал `updateConfigs`, очищал лист `Configs` и записывал 0 счетов.
* **Решение:**
  * Во всех функциях управления транзакциями (`addTransaction`, `updateTransaction`, `deleteTransaction`) расчет обновленного состояния счетов `updatedAccounts` перенесен в синхронную область перед вызовом диспатча состояния.
  * На фронтенде добавлен сторожевой фильтр: `const accountsToSync = updatedAccounts.length > 0 ? enrichAccountsWithUSD(updatedAccounts) : undefined;` — пустые массивы счетов больше никогда не отправляются.
  * В `api/sheets.ts` вызов `updateConfigs` строго ограничен: `Array.isArray(payload.accounts) && payload.accounts.length > 0`.
  * Внутри `updateConfigs` внедрена превентивная защита: если в пейлоаде отсутствует или пуст список счетов, категорий или доходов, сервер предварительно вычитывает существующие строки с листа (`Configs!A1:M150`) и объединяет их, запрещая затирание существующих данных. Если все секции пусты, операция очистки отменяется.

### 2. Корректная сортировка ленты операций внутри дня (Reverse Chronological)
* **Проблема:** В «Ленте (истории)» внутри дня операции сортировались снизу вверх (старое событие дня сверху, свежее внизу), в то время как требовалось отображать последнее событие дня сверху.
* **Решение:**
  * В `src/hooks/utils.ts` создана утилита `sortTransactionsDesc(txs)`, которая безопасно сортирует транзакции сначала по дате/времени (ISO/строка), а при совпадении времени — по ID транзакции (убывание).
  * Функция покрыта 5 unit-тестами в `src/hooks/__tests__/utils.test.ts` (проверены ISO-даты, даты с русским текстом, сортировка по ID и пустые списки).
  * Функция подключена в `HistoryModal.tsx` и `CalendarAnalyticsModal.tsx`.

### 3. Исправление ошибки 403 (master_sheet_restricted) для владельца
* **Проблема:** При попытке войти в личную финансовую таблицу через веб-интерфейс, совпадающую с `MASTER_SS_ID`, сервер возвращал ошибку `403 Forbidden` (`master_sheet_restricted`).
* **Решение:**
  * В `api/sheets.ts` блокировка мастер-таблицы сужена исключительно до деструктивной операции `initTable`. Операции чтения финансового листа для владельца разблокированы.

## 📌 Ребрендинг RAG-online -> easyfaq.online & Исправление багов (30.05.2026)

### 1. Исправление языкового бага на старте (English start on Russian active switch)
* **Проблема:** При первой загрузке страницы пользователь видел интерфейс на английском языке (дефолтный хардкод в `index.html`), хотя кнопка переключения языка отображалась как активная на **RU**. Метод перевода запускался только по клику на кнопку смены языка.
* **Решение:** 
  * В `script.js` выделена функция `translateDOM()`, осуществляющая моментальный локальный перевод всех элементов с атрибутами `data-i18n` и `data-i18n-placeholder`.
  * Вызов `translateDOM()` добавлен первой строкой при инициализации страницы в `initSettings()` до отправки запросов к API, устраняя несоответствие без лишних сетевых вызовов.

### 2. Внедрение ребрендинга в кодовой базе
* **Изменения в `index.html`:** Обновлены теги `<title>`, SEO-описание, ссылки `canonical`, теги Open Graph (`og:url`, `og:title`, `og:image`), метатеги Twitter, JSON-LD Schema и суффикс регистрируемого домена с `.rag.reloto.ru` на `.easyfaq.online`.
* **Изменения в `script.js`:** Обновлена логика редиректа на успешную регистрацию: `https://${data.subdomain}.easyfaq.online`.
* **Изменения в `server.py`:** Модернизирован механизм Tenant Resolution. Теперь бэкенд на лету разрешает хосты как по `.easyfaq.online`, так и по `.rag.reloto.ru` (для обратной совместимости старых клиентов).
* **Синхронизация с сервером:** Изменения успешно закоммичены и отправлены на сервер по Git-деплою. Сервис `rag-online.service` автоматически перезапущен.

### 3. Выпуск SSL Let's Encrypt для easyfaq.online
* **Проблема:** Из-за отсутствия A-записи для `www.easyfaq.online` стандартный плагин `--nginx` падал по ошибке авторизации.

## 📌 Замена API-ключа и миграция на Google Gemini API (22.06.2026)

### 1. Смена API-ключа в конфигурации
* **Проблема:** Требовалось обновить API-ключ в проекте.
* **Решение:** 
  * В файле `.env` (и на VPS в `/opt/easyFAQ.online/.env`) значение `OPENROUTER_API_KEY` заменено на новый ключ `[REDACTED_API_KEY]`.
  * В доступы проекта (`!Docs/logins к easyfaq.md`) внесена запись о новом ключе с именем `easyFAQ` (free tier ai.dev).
  * Новый ключ зафиксирован глобально в `vault.json` через менеджер памяти (`manager.py`).

### 2. Перевод эндпоинтов на Google Gemini API
* **Проблема:** После замены ключа сайт отдавал ошибку `AI connection error`. В логах бэкенда отображалась ошибка `Chat error: 'choices'`. Это происходило из-за того, что новый API-ключ предназначен для Google Gemini API, а запросы отправлялись на эндпоинт OpenRouter (`https://openrouter.ai/api/v1/chat/completions`), который возвращал 401 ошибку.
* **Решение:**
  * В файле `server.py` заменены все три вызова API с OpenRouter на OpenAI-совместимый эндпоинт Google Gemini: `https://generativelanguage.googleapis.com/v1beta/openai/chat/completions`.
  * Имя модели заменено с `"google/gemini-2.5-flash-lite"` на `"gemini-2.5-flash-lite"`, как требует спецификация Google.

### 3. Исправление падения парсера ошибок (TypeError)
* **Проблема:** При не-200 кодах ответа от Google API (например, 429 при исчерпании лимитов free-tier или 503 при перегрузке) бэкенд падал с ошибкой `TypeError: list indices must be integers or slices, not str` при попытке обратиться к `choices` в массиве ошибок.
* **Решение:**
  * В обработчике `chat_proxy` добавлена проверка `resp.status_code != 200`. При её срабатывании в консоль пишется тело ошибки, а клиенту возвращается корректная строка `"AI connection error"`, исключая падение парсера.
  * После успешного деплоя работа чата проверена локальным curl-запросом к VPS — ИИ-ассистент работает корректно.
